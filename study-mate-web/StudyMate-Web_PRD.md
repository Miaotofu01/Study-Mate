## 1. 模型提供商

### 1.1 数据模型

系统支持配置**多个模型提供商**，其中一个处于"当前使用"状态。

- 提供商条目包含：名称、类别（预设 / 自定义）、Base URL、API Key、API 格式（三选一，见第 2 节）、模型列表、启用开关、创建时间。
- 模型列表：每项包含模型名（发送给 API 的 id，即 ZCode 口径的"模型 ID"）、显示名（可空，空则显示模型名）、**输入模态**（文本 / 图片 / 视频 / PDF 四项布尔，见第 3 节）、上下文窗口、**最大输出 Token**（见 §2.1）、**推理档位**（有序档位名列表 + 默认档位，见 §2.1）、能力声明（工具调用 / JSON Schema 输出 / 原生联网搜索；**工具调用默认对所有配置的模型开启**（2026-10-04 定档），不再是可选项，上游拒绝 tools 参数时自动回落纯文本，见第 14 节；其余两项仅落盘与展示）、启用开关；每个提供商至少保留一个模型。
- 当前使用状态是"提供商 + 模型（+ 当前推理档位）"三元组，全局生效。
- 停用的提供商不能被设为当前使用，其模型不出现在对话侧的模型选择里；当前使用的模型被停用时，自动回落到该提供商第一个可用模型。
- 模型字段的取值口径**对齐 ZCode**（`properties.inputFormat` / `properties.contextWindow` / `optionSpecs.maxOutputTokens` / `optionSpecs.reasoningLevel`）：模态是多值布尔而不是单选，推理档位是**用户可自由编辑的有序字符串数组**（不写死成固定档位枚举）。
- 预设提供商固定四种：DeepSeek、SiliconFlow、DashScope、OpenAI；预设条目不可删除，但所有字段（含 API 格式）可修改，并提供"恢复默认"；自定义条目可增删改。
- 配置持久化在 `<study-mate-web>/data/settings.json`；系统提示词是独立于提供商的顶层配置项（见第 6 节）。

### 1.2 兼容与迁移

- 旧版单提供商结构在读取时自动迁移为多提供商结构：原配置成为一条提供商记录、其模型名成为该记录模型列表第一项、当前使用指向它；API Key 不丢失。迁移对用户无感。
- 模型的旧字段同样在读取时等价迁移：`视觉覆盖（自动 / 支持 / 不支持）` → 输入模态（"自动"迁为**未配置**，仍走内置前缀表，行为不变）；`思考档位（关 / 低 / 中 / 高）` → 推理档位（关迁为"未启用"；其余档位成为 `off/low/medium/high` 这组档位里的默认项）。缺字段按默认值补齐，读取不报错，迁移结果幂等落盘（不会反复重写）。
- 环境变量 `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL` 在运行时覆盖当前使用提供商的对应字段，优先级最高，不写回配置文件。

### 1.3 提供商页（设置的默认子页）

提供商页采用**主从布局**（左列列表 + 右列编辑区；形态对齐 ZCode 的提供商页）：

- 左列为提供商列表：每项显示名称、API 格式徽标、**可用**模型数量；当前使用的项带"使用中"标识；列表上方有名称搜索框，底部有"添加提供商"。
- 右列编辑器（与添加面板互斥）：
  - **头部**：提供商图标、名称、**启用开关**，以及"…"菜单——菜单收纳"设为当前使用"、"恢复默认"（仅预设）、"删除"（仅自定义），不额外发明功能。
  - **连接区**：名称、Base URL、API 格式下拉（"OpenAI 兼容 Chat Completions" / "OpenAI Responses" / "Anthropic Messages"）、API Key（**回填已保存的密钥**，以密码点显示、右侧"显示 / 隐藏密钥"可切明文，不把密钥从界面上"吞掉"）。
  - **模型区**：模型列表为**只读摘要行**——模型名 + 徽标（上下文窗口如 `1M` / `128K`、模态、`思考 · <档位>`）+ 右侧四个操作：**测试**（该模型连通性）、**编辑**（打开模型编辑弹窗）、**删除**、**启用开关**；右上角"＋ 添加模型"。行内不直接编辑。
- **模型编辑弹窗**（字段与分区对齐 ZCode，见 §1.1）：
  - **基础区**：模型 ID、显示名、**输入模态（复选框组：文本 / 图片 / 视频 / PDF，可多选，不是单选下拉；未配置过模态的模型默认勾选「文本」）**、**最大输出 Token**（默认 32000）、上下文窗口（默认 2560000）。
  - **高级（可折叠）**：**推理档位的有序 chip 编辑器**（可添加 / 删除 / 改名 / 排序）、默认档位——启用推理档位时若尚无档位，自动预置 `disabled / enabled` 两档并**默认档位取最高档**；能力声明——**工具调用默认对所有模型开启**（界面作为只读项提示，不提供开关；上游拒绝 tools 时自动回落纯文本），JSON Schema 输出 / 原生联网搜索两个开关仅落盘与展示。
  - **不提供"智能配置"**（不做任何自动探测 / 自动推断模型能力，模态、上下文窗口、最大输出 Token 一律人工填写）；**不提供模型级"启用"开关**（启停在模型行的开关上做）。
- **实时生效**：编辑器（含添加面板与模型编辑弹窗）的改动**防抖落盘、无「保存」按钮**，头部只给"保存中… / 已保存"的轻量反馈；连接测试也不再占编辑器底部按钮（入口见 §1.4）。新建提供商会立即落盘。
- 添加流程：右栏出现添加面板，从四个预设与"自定义"中选择后生成条目并进入编辑。

### 1.4 连接测试

以**模型行为单位**发起（编辑器底部不再有「测试连接」按钮）：按该提供商当前表单值 / 已落盘值向目标端点发一次最小请求，成功显示往返耗时，失败显示上游错误摘要。

- **API Key 取用**：编辑器加载时把**已保存的密钥回填进输入框**（用户看得见、能改、能测）；测试时以输入框的值为准，输入框被清空时才回落到该提供商已保存的 Key——因此"已保存过 Key 的提供商"不会误报"缺少 API Key"。
- 既没有输入值、也没有已保存 Key 时才报"缺少 API Key"。
- 掩码 `********` 仍被接受为"不修改"（PUT 的向后兼容语义），但界面不再用它做回显。
- 模型行上的"测试"走同一套判定，针对该行模型发起。

## 2. API 格式适配

系统通过统一适配层支持三种 API 格式，聊天（流式）与判分 / 评估 / 摘要 / 科目生成（非流式）等所有模型调用都经过它：

- **OpenAI 兼容 Chat Completions**：请求发往 `{base}/chat/completions`，流式响应逐段取文本增量；JSON 输出模式走该协议的结构化输出参数。
- **OpenAI Responses**：请求发往 `{base}/responses`；系统提示词走 instructions；流式拼接 `response.output_text.delta` 事件；JSON 输出模式走该协议的结构化文本配置。
- **Anthropic Messages**：请求发往 `{base}/v1/messages`，鉴权头为 `x-api-key` 与 `anthropic-version`；系统提示词走独立 system 参数；最大输出 tokens 必填（默认 4096）；流式取 `content_block_delta` 的文本增量；JSON 输出模式不可用，以提示词约束与宽容解析替代。
- 消息内容采用统一的内部表示（文本与图片块），由适配层按格式翻译为各协议的请求结构。
- 客户端超时 60 秒；上游错误信息原样透出给上层。

### 2.1 推理档位与协议映射

推理档位是**模型级能力**：每个模型声明一组**有序档位名**（由用户在模型编辑弹窗里自由增删改与排序，例如 `off/low/high/max`）与一个默认档位；对话侧在**输入区工具条、模型选择器右侧有一个独立的档位下拉**（2026-10-04：原在模型弹层底部的档位 chip 已移除，档位只有这一个入口；当前模型没有档位时该下拉整体隐藏），切换写回当前使用三元组。

- 档位到各协议的参数映射由统一适配层完成：Chat Completions 走 `reasoning_effort`；Responses 走 `reasoning.effort`；Anthropic 走 `thinking: {type: enabled, budget_tokens}`（预算按档位取值，并把 `max_tokens` 抬到预算之上以满足协议对 `budget_tokens < max_tokens` 的要求）。
- **模型未启用推理、档位列表为空、或档位为 `off` 时不发送任何思考参数**，请求体与未启用该能力的实现完全一致；无法识别的档位值静默省略而不是把请求打挂。
- OpenAI Responses 与 Anthropic 在开启推理时不再发送 `temperature`（这两类推理模型对非默认 temperature 会直接报 400）。
- **最大输出 Token** 同样由模型声明：非空时作为该模型的输出上限（Anthropic 的 `max_tokens`、其他格式的对应参数），为空则沿用默认值。
- 该能力为模型级声明，不改变聊天以外的调用（判分 / 评估 / 摘要 / 生成）。

### 2.2 工具调用协议映射

当一次调用带工具声明时，适配层按标准 OpenAI function calling 的 wire 形态翻译各协议（不发明自定义 wire 格式）：

- **Chat Completions**：`tools[{type:function,function:{name,description,parameters}}]` + `tool_choice`；assistant 的 `tool_calls{id,type,function{name,arguments}}`（arguments 为**原始 JSON 字符串**）与 `role:tool` + `tool_call_id` 回传。
- **Responses**：`tools[{type:function,name,description,parameters}]`；工具调用与结果表示为 `function_call` / `function_call_output` 输入项（以 `call_id` 关联）。
- **Anthropic Messages**：`tools[{name,description,input_schema}]` + `tool_choice:{type:auto}`；assistant 的 `tool_use` 块与 user 侧 `tool_result` 块（连续结果合并进一条 user 消息，`tool_use_id` 关联）。
- **流式增量聚合**：按 wire `index`（Responses 按 item id）聚合；`id` / `name` 赋值不追加、`arguments` 拼接，协议给出完整块时以完整值为权威（防止网关重复发 id 撑爆参数）。
- **降级**：`tools` 参数本身被上游拒绝（400）时，自动回落一次不带 tools 的调用。

## 3. 模态能力与自动剔除

设计原则：**输入端不拦截，发送端按能力注入，失败后按错误降级**（对照 DeepTutor 的两段式）。

### 3.1 能力判定

- 模型的视觉能力 = 该模型的**输入模态**优先：配了模态就用其中的"图片"项（显式配置压过内置表）；**未配置模态**时查内置模型前缀表——命中已知视觉模型（gpt-4o 及以后、gpt-4.1+、o3/o4 系列、claude-3+、claude-4+、gemini、glm-4v、qwen-vl、deepseek-vl 等）视为支持，未命中默认不支持。前缀表在后端单处维护。
- 模态里的"视频 / PDF"当前只做落盘与展示，发送侧行为不变（视频 / 音频一律文本占位，见 §3.2）。

### 3.2 发送端第一段（按能力注入）

- 模型支持视觉：图片按当前 API 格式转换为对应内容块随消息发送（Chat Completions 用 data-URL 图片块；Responses 用 input_image；Anthropic 用 base64 图片块）。
- 模型不支持视觉：不注入图片块，在消息文本对应位置插入占位行——"[图片：<文件名> —— 当前模型不支持图片输入，已剔除]"，并向前端发送提示。
- **视频与音频一律按"不支持"处理为文本占位，不实际发送**（三种协议对视频 / 音频输入的支持差异大、可用面窄，此为有意裁剪）。

### 3.3 发送端第二段（错误码剔除重试）

- 当请求携带图片块且调用失败时，对上游错误文本做标记匹配（image / vision / multimodal / image_url / content type / must be a string / expected string / invalid type for 'messages' 等，可结合 400/422 状态码）。
- 命中且模型不在已知视觉名单：剔除全部图片块、替换为占位行，**重试一次**；重试成功则向前端提示"模型不支持图片输入，已自动剔除并重试"。
- 模型在已知视觉名单上：**不降级**，让真实错误原样暴露（避免把真错误吞成误导性的纯文本回答）。
- 重试至多一次；再失败按普通错误处理。

### 3.4 提示事件

- 流式对话新增 `notice` 事件，承载"已剔除 / 已重试"类非致命提示；前端渲染为消息流中的浅色提示条，不写入会话历史。

## 4. 附件

### 4.1 输入入口

- 聊天输入框左侧**单一 📎 按钮**，文件与图片统一走此入口；支持点选、拖拽到输入区、粘贴。
- 受理范围：`image/*`（SVG 例外归入文档类，因视觉模型不收 SVG）+ 文本类（md / txt / csv / json / xml / 常见源码）+ pdf / docx / xlsx / pptx / epub。
- 支持多选；单附件上限 20MB，单条消息附件数上限 10 个，超限即时提示。
- **仅附件、无文字也允许发送**。

### 4.2 上传与存储

- 消息发送前先上传：`POST /api/uploads`（multipart），返回附件标识、文件名、大小与类别（图片 / 文档）；消息体引用附件标识。
- 存储位置：`<study-mate-web>/data/uploads/<会话>/<附件标识>_<文件名>`；消息记录中保存附件元数据。
- 删除会话时连带删除其上传目录；已上传但始终未随消息发送的孤儿文件，由后端启动时清理（超过 24 小时的未引用文件）。

### 4.3 文档解析

解析目标以**功能齐全**为主，在后端实现"字节进、文本出"的确定性管线（对照 DeepTutor 的 document_extractor）：

- **文本类**（md / txt / csv / json / xml / 源码）：多编码回退解码后原样注入。
- **Office 二进制**：pdf 用 pymupdf（缺失回退 pypdf，皆缺则"未解析"占位）；docx 用 python-docx；xlsx 用 openpyxl；pptx 用 python-pptx。解析库列入依赖清单，缺失时优雅降级为占位并提示。
- **EPUB**：标准库 ZIP + OPF 顺序提取。
- **注入方式**：附件提取文本以"附件：<文件名>"为标题块，拼接在用户消息原文之后，随消息进入会话历史与模型上下文。
- **预算**：单附件提取文本上限 20000 字符，单条消息全部附件合计上限 60000 字符，超限截断并提示。
- **解析失败**：注入"[附件 <文件名> 解析失败：<原因>]"占位，不阻断发送。
- 与插件侧的关系：Study-Mate 插件的本地教材转换是 resource-scout 第 0 步的**流程约定**（转 markdown 落 `reference/`，工具由总控准备），本节是 Web 运行时自己的确定性解析，**不改变插件侧流程**。文档内嵌图片不提取；OCR 不做。

### 4.4 前端展示

- 输入框上方横向**附件 chips 行**：图片显示本地缩略图，文档显示图标 + 文件名 + 大小；每项可移除。
- 消息流中，用户消息下方渲染该消息的附件：图片缩略图（点击放大预览），文档名（点击下载）。

## 9. 工作区与发现

Web 与插件**共用同一套工作区与发现规则**，布局与插件 `.learning` 同构：

- **布局**：`<工作区>/.learning/subjects/<slug>/` 下放科目 yaml、`lessons/`、`reference/`、`assets/`、
  `assessments/`、`learning-records/`、`sessions/`；工作区级共享资源在 `<工作区>/.learning/assets/`。
- **发现**：复用上游 `scripts/gen_home.py::learn_workspace()`，Web 不实现第二份规则。优先级：
  显式 `STUDYMATE_WORKSPACE` > `LEARN_WORKSPACE` > `STUDYMATE_CONFIG`（默认
  `$DSH_HOME/studymate-config.yaml`）的 `workspace` 字段 > 插件默认 `~/StudyMate`。
  上游发现不可用（无配置/脚本缺失）时回落到 `~/StudyMate` 并记警告，不阻断启动。
- **不自动种入示例**：Web 不再往工作区拷 `backend/seed/` 示例科目——默认工作区可能正是插件在用的目录，
  往其中写示例数据是不允许的副作用。示例只供建课演示与 E2E fixture 使用；工作区为空时课程页显示空态。
- **设置页「工作区」子页**：展示当前路径、来源、科目目录、配置文件位置与科目数；
  可改选目录——写入 `studymate-config.yaml` 的 `workspace` 键（行级替换，保留注释与其它键），
  保存后立即生效（无需重启）；写入失败以 422 透出原因，配置与目录创建失败时回滚到改前内容。
- **新会话内选工作区（2026-10-04 改形态）**：原「选择学习工作区」欢迎区引导块已移除，改为**新对话态输入区上方的关联行**里的「工作区」下拉（与「关联科目」并排，见 §5.1）——空选项 = 当前默认工作区，候选 = 发现路径 / 插件默认 `~/StudyMate` / 环境变量覆盖值（去重），选中即按该工作区重载科目列表。
- **会话级工作区绑定（2026-10-04 拍板"甲"）**：会话可各自绑定一个工作区（绝对路径，存会话元数据；null = 跟随当前默认工作区）。绑定的作用是**该会话内的一切科目读写都落在它自己的工作区里**：对话的课程上下文、开场切片与记忆读取、会话小结与评估的落盘、附件区清单与原文，全部按该会话的工作区解析；打开历史会话时前端会切到它绑定的工作区加载科目列表。后端实现上只有一个收口点（`curriculum_store` 的工作区解析读请求级绑定），科目类读接口可带 `?workspace=<绝对路径>` 显式指定；`GET /api/workspace?path=` 提供只读预览。**约束**：绑定要求目录已存在（否则 422）。
- 工作区目录按需创建；`STUDYMATE_WORKSPACE` 存在的机器上，设置页改选不会改变实际生效路径
  （env 优先级最高，页面如实展示来源）。

  （仓库 `.dsh/skills/`）。

## 11. 开场切片与学习记录

- **节点聚焦自动推断（2026-10-04）**：课程上下文的"当前节点"在会话未指定节点时由后端按进度推断（学习中 → 第一个未开始 → 无），使默认对话即聚焦"接着上次学"的节点；显式指定（如节点详情「问 StudyMate」带入）优先。
- **开场状态切片**：会话首条消息且已关联科目时，后端自动组装并注入"恢复视图"子集——
  共享记忆分节（`MEMORY.md`）+ 最近 5 条误解 + 最近 3 条学习记录 + 最近 3 条评估记录；
  数据缺失的节自动省略。课程上下文（科目/节点/进度）仍按原样注入。
- **对话节奏**：总控规范（注入的 `learning-system`）要求每轮回复以「下一步」收尾；
  E2E 以 fixture 回复的「下一步」行为锚点守住呈现链路（真实 LLM 下的质量由手动/冒烟验证）。
- **评估联升**：评估结论"通过"是权威置位——该节点置为"能独立应用"（实验课为"已通过项目验证"），
  **实验课通过时同时把 `prerequisites` 里的被验收节点一起置为"已通过项目验证"**（掌握度保留或按评估建议上调）。
- **学习记录**：评估通过时写一条 `learning-records/<序号>-<节点id>.md`（"仅可观察证据时写"，
  当前唯一自动入口是评估通过；评估作答原文即可观察证据）。
- **摘要同日多段追加**：会话小结落 `sessions/<YYYY-MM-DD>.md`；同日再次小结时保留首个 front matter，
  在正文追加"本场摘要（HH:MM）"分段，不覆盖已有内容。
- **附件区**：`GET /api/courses/<slug>/attachments-area` 返回术语表（`GLOSSARY.md`）、
  `reference/`、`learning-records/`、`sessions/` 的清单；聊天页右侧边栏列表展示，项点击新标签页
  打开原文件（内容经 `/files/` 端点）。空组不渲染，四组全空显示空态。清单与文件读取都按**该会话绑定的工作区**解析（未绑定则当前默认工作区）。

## 12. 共享记忆写侧（MEMORY.md）

- **建议**：`POST /api/memory/suggest` 从指定会话提炼"值得长期记住"的条目

- **读侧**：MEMORY.md 分节经开场状态切片（§11）进入对话上下文。

## 13. 生产侧（产课 / 建课 / 采图 / 方向探索 / 质检工单）

Web 除"消费已有产物"外，还以**角色子代理**形态承担生产职责：后端发起一次角色派工，
system = 角色技能规范（`.dsh/skills/<名>/SKILL.md`）全文 + 运行环境适配声明，user = 派工值；
上游检查脚本（`render_lesson.py` / `check_lesson.py` / `check_curriculum.py` / `check_pool.py` /
`gen_home.py`）以子进程零重写复用。派工回复走 JSON envelope（`{files:[{path,content}], data, report}`），
逐字落 `.stage/<角色>-<节点>/deliver/` 再搬正式位。

> 子代理形态分两支：**工具化 agent 循环**（默认，对所有配置的模型开启，第 14 节）与**无工具单次调用**
> （工具循环无交付时的回落兜底 / fixture 模式下的既有 envelope 契约）。K 系列起，建课链与产课链
> 按此分流，交付契约与检验收口不变。

- **节点产出（产课链）**：课程图谱页节点详情发起，SSE 把阶段进度（讲解派工 → 出题派工 →
  渲染 → 检查）实时播报进会话消息。按大纲顺序推进（上游检查器要求课件编号连续）。
  渲染/检查失败按产物路径归属打回重派（上限 2 轮，重派附报错原文证据）；派工 envelope
  契约失败（模型偶发畸形）同样原值重派。耗尽转**质检工单**。
- **建课（开课链）**：chat 内建课会话（`mode=interview`，注入学习系统 + 方向探索规范），
  盘问收口后建**草稿区**（`data/drafts/<slug>/`，科目同构布局）并在会话落「确认建课」卡；
  建课编排 = 资料落盘 → 大纲派工与采图并行 → `check_curriculum.py` 门禁 → done 落「落点确认」卡，
  确认后 promote 到工作区 `.learning/subjects/<slug>` 并跑 `gen_home.py` 刷主页。
- **采图**：建课编排内按配额从公网URL采集图片（robots 遵守 / 私网地址拒绝 / 每文件限额），
  落 `assets/img/` 与索引 `pool.md`，讲解派工值内联索引供课件配图引用。
- **方向探索**：chat 内可选入口（探索期不写盘），回答末尾给「去建课」动作。
- **质检工单**：转人工后的两段式模态——总览按归属分组列出问题，逐项可快改（仅科目目录内
  相对路径）或仅重试该项；`POST .../recheck` 复检外部改过的文件、`retry` 带证据重派。
  转人工是常态兜底：上游检查器比现阶段模型更严格，真实 LLM 冒烟中两个参评模型最终都落工单。
- **真实 LLM 选型口径**（2026-10-03 实测）：产出链（后台编排）优先速度，用
  space-bunny-alpha（两节点约 3 分钟）；质量敏感面（对话 / 评估）用 mimo-v2.6-flash
  （单节点约 40 分钟）。参评模型均带思考档位；渠道约定串行不并发。

## 14. 工具化调用（Agent 循环）

系统对**所有配置的模型**默认采用**工具化 agent 循环**替代单次大派工（对齐插件基线的 harness 形态）。
循环终止判据是"某轮不再发起工具调用，其文本即最终答案"。

- **轮次预算**：探索 8 轮（工具可用）+ 收尾 3 轮（工具仍可用，但注入"尽快收尾"提示）+ 强制无工具收尾 1 轮；
  "只思考不行动"（某轮既无文本也无调用）最多救 2 次；连续 3/5/8 次完全相同的调用发提醒（不阻断）。
  预算耗尽仍无最终答复时降级：带已有内容收尾并给出提示。
- **工具失败**一律转成 `role:tool` 的错误文本回喂，让模型自愈，不中断循环；单次结果超限截断。
- **文件边界**：相对路径以会话工作区 / 科目目录为基准；写操作前当场重新规范化并校验包含关系；
  越界返回稳定的可读拒答标记。加宽边界只有"转质检工单 / 人工确认"一条通道，不开放自由路径。
- **审计**：同一份事件序列既推前端又追加写 `data/audit/<编排或会话 id>.jsonl`——派工值、模型原始回复、
  每次工具调用与结果都落盘，**失败不清除**（供事后审计与堵点定位）；敏感参数在工具声明处脱敏。
- **chat 链路（只读工具）**：`list_workspace` / `read_course_file` / `read_skill`，读根限已绑定科目目录
  或工作区科目目录、以及仓库 `.dsh/skills`；工具调用与结果以**可展开工具卡**呈现在会话流里（兼审计 UI）。
- **建课链**：大纲角色用 `submit_curriculum` 提交 DAG，后端**立即跑门禁并把报错原文回喂**，模型循环内自修；
  后端在循环之后再强制跑一次门禁（不信任模型自查）。
- **产课链**：角色用 `write_deliver_file` 交付产物、`run_check`（渲染 + 检查）在循环内自查自修；
  循环结束的交付仍走既有渲染/检查收口与质检工单兜底。
- **开启范围**：**工具调用默认对所有配置的模型开启**（2026-10-04 定档，不再是可选项）；上游若不接受
  `tools` 参数，适配层自动回落一次不带 tools 的纯文本调用（工具声明本身不会打挂请求）。fixture 模式下
  仅显式工具场景走循环、其余保持固定流（测试稳定）。
- **不变量**：SKILL.md 全文注入保留（另加 `read_skill` 按需补充）；上游脚本零重写；门禁由后端在写盘后强制执行；
  采图保持纯后端爬虫，不进角色体系；工具循环无交付时回落既有单次派工链兜底。
