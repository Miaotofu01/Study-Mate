# 领域文档

探索本仓库代码库时，工程类技能该怎么消费这里的领域文档。

## 动手前先读

- 仓库根的 **`GLOSSARY.md`** —— 领域词表；或
- 仓库根的 **`GLOSSARY-MAP.md`**（存在时）—— 它指向每个上下文一份 `GLOSSARY.md`，读与当前话题相关的那几份；
- **`docs/adr/`** —— 读与你要动的区域相关的 ADR。

**这几份还不存在时，静默跳过。** 不要提它们的缺失，也不要主动建议先建起来。它们由 `/domain-modeling`（经 `/grill-with-docs` 与 `/improve-codebase-architecture` 到达）在真的定下术语或决策时**按需创建**。

## 本仓库的布局：单上下文

本仓库没有 monorepo 信号（无 `pnpm-workspace.yaml`、`package.json` 无 `workspaces` 字段、无 `packages/*`），因此采用**单上下文**：

```
/
├── GLOSSARY.md          ← 项目级领域词表
├── docs/adr/            ← 架构决策记录（按需创建）
│   └── 0001-<决策>.md
├── docs/规范/           ← 唯一约束来源
└── preset/skills/       ← 角色与协议规格（宿主默认不扫这里）
```

**词表已建立**：新术语写进 `GLOSSARY.md`；`docs/adr/` 按需创建，有决策时才写进去并按序编号。

## 别把「文件归属」当成词表

`docs/规范/文件归属.md` 是**文件代称、路径、维护者**的唯一出处（总控、讲解、出题评估这些**角色代称**也在它里面）。`GLOSSARY.md` 管的是**领域语言**——「科目」「节点」「课件内容文件」这类概念该怎么称呼。

两者职责不重叠，也**互为补充而非替代**。写 issue 标题、重构提案、假设或测试名时：

- 涉及**文件或角色**的叫法 → 以 `docs/规范/文件归属.md` 为准；
- 涉及**领域概念**的叫法 → 以 `GLOSSARY.md` 为准（还没有这份、且你确实需要一个新词时，那是 `/domain-modeling` 的信号）。

**一条硬规矩照旧：一处定义，别处只给指针。** 不要把 `文件归属.md` 的内容抄进 `GLOSSARY.md`。

## 用词表里的词

你的输出要提到某个领域概念时（issue 标题、重构提案、假设、测试名），**用 `GLOSSARY.md` 里定义的叫法**，别漂到它明确避开的同义词上。

如果你需要的概念不在词表里，那是个信号：要么你在发明项目不用的语言（再想想），要么这里真有缺口（记下来交给 `/domain-modeling`）。

## ADR 冲突要摆到台面上

你的输出若与某条既有 ADR 矛盾，明确说出来，不要悄悄覆盖：

> _与 ADR-0007（事件溯源订单）冲突，但值得重开，因为……_
