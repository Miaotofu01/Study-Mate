# 编排纪律

**范围内**：在本仓库里编排开发活（派活、等下属、跑门禁）的 agent。**这份是它的唯一出处**——AGENTS.md 只给指针。

**术语**
- **一票** —— 一个分支/一个 PR 的一次完整交付。
- **子集** —— 由覆盖率算出来的、真的会把这次改动拉进来的套件。算不出来的叫猜。
- **检查点** —— 一次便宜且高信息的抽样：看产物，不看回显。

## 一、等下属：结束轮次，让通知唤醒

1. 派活前武装 continuation：`create_goal` 按预计唤醒次数留足 `max_goal_rounds`；fork/resume 之后 `update_goal action=resume`。
2. 派完就结束轮次，把「谁跑完了」交给完成通知。
3. 预计超过 20 分钟的任务，在 1/3 处设一个检查点。
4. N 个下属包成一个 workflow（一个 job = 一次唤醒）；同时挂着的后台 job 保持个位数。

**例外**：返工贵的（大范围写盘、外部抓取）或会静默跑偏的（网络、限流、代理），检查点必留。

## 二、一轮发多个工具调用

1. 已经知道要读哪几份时，一轮发 3–5 个 `read` / `grep` / `glob`。
2. 不知道读哪份时，先 `grep` 定位，再一轮把命中文件读掉。
3. 大文件带 `offset` / `limit`。

**例外**：有依赖链的（先 `glob` 才知道路径）、参数不确定的（`bash`、`write`）老实串行。

## 三、全量套件一票只跑一次

1. 中途跑子集。
2. 全量一票跑一次，在收工前；那之后 base 不再动，门禁读数对应那一次。
3. 每个 ticket 收尾设一个检查点：子集 + 一条冒烟。
4. 日常改动取小：子集按覆盖算，不按「同目录 / 同类型」猜；算不出覆盖就退回全量。
5. 变异验证取大：它回答的是「套件里有没有测试能挡住这个缺陷」，用猜的子集证伪会得出错结论——跑覆盖率里真的把该文件拉进来的**全部**套件（口径见 `scripts/tests/test_core_coverage_floor.mjs`，它 spawn 的是 `node --test --test-coverage-*`）。

## 四、一个仓库目录

活就在你自己的仓库目录里干：开个分支，干完切回 `main`，别为它另开一个目录——另开的目录谁都看不见，等于没干。
