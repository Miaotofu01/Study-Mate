# 编排纪律

**范围内**：在本仓库里编排开发活（派活、等下属、跑门禁）的 agent；**这份是它的唯一出处**，AGENTS.md 只给指针。

**术语**
- **一票** —— 一个分支或一个 PR 的一次完整交付。
- **子集** —— 由覆盖率算出来的、真的会把这次改动拉进来的套件。
- **检查点** —— 一次便宜且高信息的抽样，看产物，不看回显。

## 一、等下属：结束轮次，让通知唤醒

派活前给 `create_goal` 按预计唤醒次数留足 `max_goal_rounds`、fork 或 resume 之后补一次 `update_goal action=resume`，派完就结束轮次、把「谁跑完了」交给完成通知，超过 20 分钟的任务在三分之一处留一个检查点，多个下属包成一个 workflow，返工贵的或会静默跑偏的活检查点必留。

## 二、一轮发多个工具调用

知道要读哪几份就一轮发 3–5 个 `read` / `grep` / `glob`，不知道就先 `grep` 定位再一轮把命中的读掉，大文件带 `offset` 或 `limit`，有依赖链的与参数不确定的老实串行。

## 三、全量套件一票只跑一次

中途只跑子集，全量在收工前跑一次且跑完 base 不再动，每个 ticket 收尾留一个检查点，日常改动按覆盖率算子集、算不出就退回全量，变异验证取大（它回答的是「套件里有没有测试能挡住这个缺陷」，口径见 `scripts/tests/test_core_coverage_floor.mjs`）。

## 四、一个仓库目录

活就在你自己的仓库目录里干：开个分支，干完切回 `main`，别为它另开一个目录——另开的目录谁都看不见，等于没干。
