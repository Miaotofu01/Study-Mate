# 贡献契约降为「原则 + 指针」，并让规则回到机器能查的地方

贡献契约曾把三样东西混在一起：流程规则、工程细节、已经枯萎的剧情事实（例如「`test` 是遗留分支、PR #10 至今没合回来」——该分支已删除，那两个提交早已进 `main`）。同一事实又被抄在十几处，改一处就会留下别处的错。决定：`CONTRIBUTING.md` 作为贡献规矩的**唯一出处**，只留机器查不了、新人会问的原则，细节全部外链到各自的唯一出处；`AGENTS.md` 降为只给指针，不再复述规则。

与之配套的三个决定：

- **删掉「PR 目标分支只能是 `main`」。** 它成立的理由（`test` 遗留分支）已经消失，`main` 本就是仓库默认分支，GitHub 的 PR 表单会自动选它；而它真实的失败形态不是报错，是「基分支不是 `main` 的 PR 静默地没有 CI」。改成 CI 在所有 PR 上跑，选错基分支不再无声无息。
- **不开强制门。** 单维护者场景下，分支保护与必需检查会让你自己的热修也要绕一圈，换来的保护对没有写权限的外部贡献者本来就有限。门禁仍是唯一一条 `npm test`，靠标准与评审，不靠权限。
- **不为契约加一致性断言。** 规则写成「不出现会枯萎的剧情事实」，而不是再写一套扫描文档的断言——这套断言本身也会需要维护。

## Considered Options

- **保留 main-only，但让它在 CI 里响亮失败**：能挡住失败形态，却要多一条「只为报错而存在」的检查，且规则本身已无理由支撑。
- **机器可读的契约清单（`contract/*.yaml`），两份文档都从它生成**：查得住，但多一层要维护的格式与工具，与「轻量」相抵。
- **加断言检查契约里的链接与 npm script 是否真实存在**：价值真实，但违反同一取舍——为文档再加一条维护面。

## Consequences

- 规矩的兑现从「配置强制」退回「评审判断」：**「提交 PR 前与 `main` 同步」是唯一一条没有强制手段的硬要求**，它能兑现多久取决于每次评审是否真的开口；这是本决策最可能先失效的一处。
- 两份文件之间仍有指针关系，改规则时 `AGENTS.md` 的指针需要同步——单一事实源降低了重复，但没有消除「两处要一起看」这个结构性成本。
- 已知遗留、本次不动：`jsonschema` 不在 CI 的依赖里，schema 校验只在本地装了它时才真正执行（校验器现在会明确打印「schema 未校验」，不再假装通过）；Python 的声明下限（3.9+）与 CI 实际运行（3.13）的差距保留。
